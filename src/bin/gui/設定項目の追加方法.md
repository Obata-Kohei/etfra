# **1. 現在の実装構造**

`etfra.md` に記載されたリポジトリを確認しました。以下では、現行の `src/bin/gui/` を対象とし、廃止予定の `etfra-gui_obsolete/` は対象外とします。

今回の変更を理解するうえで重要なのは、**Settings に列挙型の値を追加することと、その値をGUIから選択可能にすることは別の作業である**という点です。

現在のGUIは、おおむね次の経路で設定変更を処理しています。

**UI (**`ui/settings.rs`**)**

設定候補を表示・選択

AppActionを生成

**Action (**`action.rs`**)**

設定変更を表現

**Controller (**`controller.rs`**)**

AppSettingsを更新し、更新種別を判定

**ComputeManager (**`compute.rs`**)**

必要な計算・描画処理を実行

**App (**`app.rs`**)**

結果を受け取りTextureを更新

この構造は、設計仕様書の「UIはActionを生成し、Controllerが状態変更と更新要求の決定を行う」という方針にも沿っています。

したがって、新しい設定を追加したときには、単にUIに選択肢を追加するだけでなく、設定値が最終的な描画処理まで伝わることを確認する必要があります。

# **2. GrayscaleInvをGUIで利用可能にする**

## **2.1 現状の問題点**

`src/bin/gui/app/settings.rs` の `ColorMapSettings` は次のようになっています。

```
pub enum ColorMapSettings {
    Grayscale,
    GrayscaleInv,
    HueGradient,
}
```

ここには既に `GrayscaleInv` が追加されています。

しかし、同じファイルの `create_color_map()` は次の状態です。

```
impl ColorMapSettings {
    pub fn create_color_map(&self) -> Palette {
        match &self {
            ColorMapSettings::Grayscale => {
                Palette::grayscale(256)
            }
            ColorMapSettings::HueGradient => {
                Palette::gradation_by_hue(
                    256, 0.0, 360.0, 1.0, 1.0
                )
            }
        }
    }
}
```

`GrayscaleInv` の分岐がありません。

つまり、GUIに選択肢を追加する以前に、描画用パレットの生成処理にも対応が必要です。

## **2.2 変更箇所① settings.rs**

まず `create_color_map()` に `GrayscaleInv` の分岐を追加します。

```
impl ColorMapSettings {
    pub fn create_color_map(&self) -> Palette {
        match self {
            ColorMapSettings::Grayscale => {
                Palette::grayscale(256)
            }
            ColorMapSettings::GrayscaleInv => {
                // Grayscaleを反転したパレット
                // Paletteの実際のAPIに合わせて実装する
            }
            ColorMapSettings::HueGradient => {
                Palette::gradation_by_hue(
                    256, 0.0, 360.0, 1.0, 1.0
                )
            }
        }
    }
}
```

ここでは `Palette` の実装に依存するため、反転方法を確定する必要があります。

例えば、パレットが色の配列を保持しているなら、要素の順序を逆にする方法が考えられます。

```
Grayscale:
[黒, 暗灰, ..., 明灰, 白]

GrayscaleInv:
[白, 明灰, ..., 暗灰, 黒]
```

なお、`GrayscaleInv` は既存のGrayscaleを反転するだけなので、フラクタルの反復計算アルゴリズム自体を変更する必要はありません。

## **3.4 AppSettingsのフィールドを追加する場合**

例えば、画像の表示品質に関係する設定として `gamma` を追加するとします。

```
pub struct AppSettings {
    pub dynamics: DynamicsSettings,
    pub image: ImageConfig,
    pub max_iter: usize,
    pub escape_radius: f64,
    pub color_map: ColorMapSettings,
    pub normalization: NormalizationSettings,

    pub gamma: f64,
}
```

これはenumのVariant追加とは少し違います。

AppSettingsは設定全体を保持する構造体なので、フィールドを追加した場合には、その値を編集するUI、Action、Controller、計算処理などを接続する必要があります。

変更箇所は以下です。

| ファイル             | 必要な変更                    |
| ---------------- | ------------------------ |
| `settings.rs`    | フィールド追加、Default値設定       |
| `ui/settings.rs` | gammaを編集するUI             |
| `action.rs`      | `SetGamma(f64)` などを追加    |
| `controller.rs`  | Actionを受けてAppSettingsを更新 |
| `compute.rs`     | gammaを使った色変換処理           |
| `controller.rs`  | 更新種別の判定を確認               |
| テスト              | 値の更新、描画への反映              |

特に注意するのは `classify_update()` です。

現在の実装では、設定の変更前後を比較し、変更があった場合に `Recompute` を返します。

```
if old.dynamics != new.dynamics
    || old.image != new.image
    || old.max_iter != new.max_iter
    || old.escape_radius != new.escape_radius
    || old_render_mode != new_render_mode
    || old.color_map != new.color_map
    || old.normalization != new.normalization
{
    return Recompute;
}
```

ここに `gamma` を追加します。

```
|| old.gamma != new.gamma
```

ただし、gammaが再着色だけで対応できる設定なら、将来的には `Recolor` と `Recompute` を区別する設計にする方が適切です。

また、`AppSettings` はJSONによる設定の保存・読み込みにも使われているため、新しいフィールドを追加した際は既存JSONとの互換性も確認します。

例えば、旧JSONにgammaが存在しない場合に備え、Serdeの `#[serde(default)]` などを検討します。

## **4.1 変更箇所① key_input.rs**

今回の主要な変更箇所です。

現在は次のようになっています。

```
if input.key_pressed(egui::Key::X)
    && render_mode != RenderMode::Survey
{
    actions.push(
        AppAction::SetRenderMode(RenderMode::Survey)
    );
}

if input.key_pressed(egui::Key::C)
    && render_mode != RenderMode::Burst
{
    actions.push(
        AppAction::SetRenderMode(RenderMode::Burst)
    );
}
```

ここにShiftキーの判定を追加します。

```
// X: Survey / Shift + X: Light
if input.key_pressed(egui::Key::X) {
    let mode = if input.modifiers.shift {
        RenderMode::Light
    } else {
        RenderMode::Survey
    };

    if render_mode != mode {
        actions.push(AppAction::SetRenderMode(mode));
    }
}

// C: Burst / Shift + C: SuperLight
if input.key_pressed(egui::Key::C) {
    let mode = if input.modifiers.shift {
        RenderMode::SuperLight
    } else {
        RenderMode::Burst
    };

    if render_mode != mode {
        actions.push(AppAction::SetRenderMode(mode));
    }
}
```

これで4種類の操作が実現できます。

なお、既存の `actions_from_input()` の冒頭には、

```
if !keyboard_enabled {
    return Vec::new();
}
```

という処理があります。

また、`app.rs` では、

```
let keyboard_enabled = !ctx.wants_keyboard_input();
```

としているため、テキスト入力中にショートカットが誤動作することも既存の仕組みで防止できます。

この仕組みはそのまま維持します。

# **5. Settings追加時の作業手順のまとめ**

今回の調査から、Settingsの追加作業を次のように整理できます。

**A. enumのVariantを追加する場合**

1. `settings.rs` にVariantを追加する。
2. `ui/settings.rs` に選択肢と表示名を追加する。
3. &#x20;必要ならパラメータ入力UIを追加する。
4. `action.rs` に対応するActionがあるか確認する。
5. `controller.rs` で設定が反映されるか確認する。
6. `compute.rs` で具体的な処理に変換する。
7. &#x20;必要ならcore側の実装を追加する。
8. &#x20;テストを追加する。

**B. AppSettingsのフィールドを追加する場合**

1. `settings.rs` にフィールドとDefault値を追加する。
2. `ui/settings.rs` に入力UIを追加する。
3. `action.rs` に設定変更Actionを追加する。
4. `controller.rs` に設定更新処理を追加する。
5. `classify_update()` に更新判定を追加する。
6. `compute.rs` などに設定値を反映する。
7. &#x20;JSONの保存・読み込みとの互換性を確認する。
8. &#x20;テストを追加する。

特に、Settingsの種類ごとに変更する場所を一覧にすると次のようになります。

| 設定                    | UI        | Controller    | Compute / Core |
| --------------------- | --------- | ------------- | -------------- |
| DynamicsSettings      | 選択肢・パラメータ | 既存Action      | Dynamics生成     |
| ColorMapSettings      | 選択肢       | 既存Action      | Palette生成      |
| NormalizationSettings | 選択肢       | 既存Action      | Normalizer生成   |
| AppSettingsの新規フィールド   | 入力UI      | 新規Action等     | 用途に応じて変更       |
| ImageConfigの新規項目      | 入力UI      | ImageConfig更新 | 描画設定への反映       |
| RenderMode            | 既存UI      | 既存Action      | 既存の解像度設定       |

## **7. 設計上の所感**

今回のコードを見る限り、設定の追加に対して比較的よい責務分離ができています。

特に次の2点は維持したいところです。

1\. **設定の種類に応じた具体的な処理は、できるだけSettings自身または対応する処理モジュールに閉じ込める。**

ColorMapSettingsなら `create_color_map()`、DynamicsSettingsなら `compute_dynamics()` という具合です。

2\. **UIはActionを生成するだけにする。**

UIからAppSettingsやComputeManagerを直接変更するのではなく、Controllerを経由させます。

一方で、現在はenumのVariantを追加すると、`ui/settings.rs` の表示名、選択肢、パラメータ処理、`compute.rs` のmatchなど、複数箇所を手動で更新する必要があります。

これはRustの網羅的なmatchによって未対応箇所をコンパイル時に発見できるという利点もあります。無理に共通化するより、現在の構造を維持しながら、追加時のチェックリストとテストを整備する方が適切だと考えます。
